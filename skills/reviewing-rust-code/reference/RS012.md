# RS012: uninformative-suppression-reason

## Problem

A suppression carries a justification, but the justification states a verdict (`"safe"`, `"intentional"`, `"false positive"`) or restates the lint (`"dead code"`) rather than the fact behind it.
This satisfies `allow_attributes_without_reason` — which only checks that a reason exists — while leaving the next reader exactly where they started.
The reason exists so that whoever revisits the suppression later, often the author, can tell whether it still holds after the code and its surroundings have drifted.
A verdict cannot be re-evaluated; a fact can.
This applies whether the justification is written as a `reason = "..."` field or an adjacent comment.

## Pros / Cons / Decision

**Pros of stating the fact behind the suppression:**
- The next maintainer can re-check the suppression when the code changes, without reconstructing the original reasoning.
- Deferred suppressions leave a trail to when they can be removed, so they don't calcify.

**Cons:**
- Requires the author to articulate *why*, not just assert that they considered it.
- "Informative enough" is a judgment call.

**Decision:**
Prefer a checkable fact over a verdict.
For a suppression deferred to later, include the condition that ends it (an issue link, version, or milestone).
A terse reason that states a genuine fact is fine — do not demand length.

## Example

### Bad
```rust
// Restates the lint — the attribute already names it.
#[expect(dead_code, reason = "unused")]
struct Cache { /* ... */ }

// A verdict with no premise — the reader still has to guess why it's safe.
#[allow(clippy::cast_possible_truncation, reason = "safe")]
let flags = raw as u8;

// "Later" with no way to know when later has arrived.
struct Router {
    #[expect(clippy::type_complexity, reason = "will clean up")]
    handlers: /* ... */,
}

// Asserts the conclusion ("can't be None") without the fact behind it.
#[expect(clippy::unwrap_used, reason = "can't be None")]
let port = config.get("port").unwrap();

// Which bound rules out the panic? The reason doesn't say.
#[expect(clippy::indexing_slicing, reason = "index is valid")]
let byte = frame[offset];
```

### Good
```rust
// The fact rustc can't see: the value comes in through deserialization.
#[expect(dead_code, reason = "constructed only via serde; rustc can't see the use")]
struct Cache { /* ... */ }

// The fact the reader must re-check if the protocol changes.
#[allow(clippy::cast_possible_truncation, reason = "value is ≤ 255 by protocol spec §4.2")]
let flags = raw as u8;

// A concrete removal trigger — and `expect` warns if it becomes unnecessary first.
struct Router {
    #[expect(clippy::type_complexity, reason = "temporary until the Response alias lands in #482")]
    handlers: /* ... */,
}

// The guarantee a reader can check: the value was just put there.
#[expect(clippy::unwrap_used, reason = "port key is inserted by load_defaults() above; always present here")]
let port = config.get("port").unwrap();

// The bound that rules out the panic.
#[expect(clippy::indexing_slicing, reason = "offset < frame.len(), checked at function entry")]
let byte = frame[offset];
```

## When to flag

- The reason restates the lint or the code (e.g., `reason = "dead code"` on `dead_code`, `reason = "unused variable"`).
- The reason asserts a verdict with no supporting fact: `"intentional"`, `"safe"`, `"needed"`, `"by design"`, `"false positive"`.
- A deferred suppression (`"fix later"`, `"TODO"`, `"temporary"`) with no concrete removal condition — no issue, version, or milestone.
- The reason would apply equally to the same lint anywhere, naming nothing specific to this site — the exception likely belongs in shared config rather than inline.
- A broad `#![allow(...)]` whose reason names neither what is special about this scope nor when it should come off.
- A panic-restriction lint (`unwrap_used`, `expect_used`, `indexing_slicing`) suppressed with a bare panic-freedom claim — `"safe"`, `"can't fail"`, `"always Some"`, `"in bounds"` — that doesn't name the guarantee. These are the lints where an unverifiable reason is most costly, since the fallback is a runtime panic.

## When NOT to flag

- A short reason that still states a genuine, checkable fact — brevity is not the problem.
- Idiomatic statement-scoped suppressions where a one-clause premise is present.
- Reasons that point to a durable reference (issue number, RFC, spec section) instead of inlining the whole explanation.
- Generated or macro code where the reason names the generator — provenance *is* the relevant fact.
- `#[allow(...)]` used deliberately over `#[expect(...)]` because the lint fires only conditionally (macro, `cfg`, target), where the reason says so.
- A panic-restriction lint whose reason names the guarantee that rules out the panic — the bound (`offset < frame.len(), checked above`), the invariant, or why the value is always `Some`/`Ok` (`literal pattern, Regex::new cannot fail`).

## Principles

The flag heuristics above fall out of a few underlying ideas. Consult these for cases the bullets don't cover.

- **Encode what the code can't show.** The attribute names the lint and the code shows what it does — the reason owes only *why it's acceptable here*. Restating the lint carries no information. (The why-not-what comment principle, narrowed to one slot.)
- **State a premise, not a verdict.** "Intentional", "safe", "by design" assert the conclusion; a premise gives a fact the reader can check — "populated only via serde, so it looks dead but isn't". A premise that records a real property of the code stays useful even if the lint later changes.
- **Explain what's local.** If the reason would excuse the lint anywhere, the exception belongs in config, not inline. Name what makes *this* site different; if you can't, reconsider the placement rather than vaguen the reason.
- **Say when it can go.** For anything temporary, a removal trigger — "remove once #1234 lands", "drop when the upstream API stabilizes" — gives the suppression a lifecycle. Without it, "not now" silently becomes "forever".
- **Anchor to what lasts.** Issue numbers, RFCs, and upstream links age well; line numbers and "see above" rot. If the explanation needs a paragraph, put it in a comment and point at it — the reason justifies the suppression, it doesn't document the code.
- **Proportionality — the one that ties the rest together.** Detail scales with surprise and blast radius. An idiomatic, statement-scoped suppression can be terse; a correctness- or security-relevant lint at module or crate scope needs the full premise plus a removal condition. Effort tracks the cost of a reader wrongly trusting the reason, not a fixed quota.

**Related rules:** RS003 `suppressed-warning` (whether to suppress and whether any justification is present), RS004 `comment-restates-code` (the same restatement failure in ordinary comments).

[^1]: Inspired by [RFC 2383 "Lint Reasons"](https://rust-lang.github.io/rfcs/2383-lint-reasons.html), whose motivation is that lint messages "explain how to make the linter program happy, but carry very little information on why the code may be a problem from a human perspective" — the reason field exists to record that human context so tools and readers can track it.
