# W007: example-over-prose

**Level:** default

## Problem

How to use an item is explained in prose that nothing checks.

Usage prose is the documentation most exposed to rot,
because it names concrete types, methods, and argument orders —
exactly the things that change.
The next signature change silently falsifies it,
and the reader who follows it gets a compile error and loses trust in the rest of the docs.

The same explanation written as a doctest is compiled and run by `cargo test`.
It cannot be wrong for longer than one CI run.

## Pros / Cons / Decision

**Pros of a doctest over prose:**
- Rot is caught in CI rather than by a confused reader.
- The example doubles as a test of the public API from the outside, which often catches ergonomic problems.
- It can be copied and run, which is what a reader wants first.

**Cons:**
- Doctests are slow to compile and run, and a large suite of them is a real cost.
- Setup-heavy APIs need `#` -hidden lines, which makes the source harder to read than the output.
- Some points are not expressible as code: when to choose this over the alternative, what the performance profile is.

**Decision:**
When documentation explains how to use something, prefer a doctest.
Keep prose for what an example cannot show.
Examples use `?` rather than `unwrap`, so that they model the code a caller should write.

## Example

### Bad
```rust
/// Builds a client.
///
/// Call `endpoint` first, then optionally `timeout` and `retries`, then `build`.
/// `build` returns an error if no endpoint was set.
pub fn builder() -> Builder {
    // ...
}
```

### Good
```rust
/// Builds a client.
///
/// # Examples
///
/// ```
/// # use mycrate::{Client, Error};
/// # use std::time::Duration;
/// let client = Client::builder()
///     .endpoint("https://example.invalid")
///     .timeout(Duration::from_secs(5))
///     .build()?;
/// # Ok::<(), Error>(())
/// ```
///
/// # Errors
///
/// Returns [`Error::MissingEndpoint`] if [`Builder::endpoint`] was not called.
pub fn builder() -> Builder {
    // ...
}
```

The call sequence is now demonstrated rather than asserted,
and it stops compiling if the builder changes.

## When to Flag

- A public item whose documentation describes a call sequence or argument shape, with no `# Examples`.
- A public item with no example at all, where a caller would need one to get started.
- An example using `unwrap` or `expect` where `?` would show the caller what to write.
- Prose naming types and methods without linking to them.
- A crate with no crate-level example showing the primary workflow.

## When NOT to Flag

- Trivial accessors and `Default` implementations.
- Private items.
- Examples that need network, filesystem, or hardware access —
  `no_run` compiles them without running, and `ignore` needs a stated reason.
- A statement genuinely outside code: complexity, thread-safety, when to prefer a sibling API.
