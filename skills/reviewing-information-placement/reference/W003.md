# W003: rationale-at-the-fence

**Level:** rule

## Problem

Some code looks removable but is not:
an explicit `drop`, a sleep, a clone that seems redundant, an odd ordering, a magic constant.
The reason it is there was written in the commit message and nowhere else.

The next maintainer deletes it,
because nobody runs `git blame` on a line before deleting it.
A commit message is unreachable at exactly the moment its content is needed —
the moment someone decides the code is pointless.
Blame is also degraded by every reformat, move, and rename that has happened since.

This is Chesterton's fence:
the reason the fence exists has to be visible from the fence.

## Pros / Cons / Decision

**Pros of recording a binding reason at the code:**
- It is present at the moment of the decision to change or remove.
- It survives file moves, re-indentation, and rewrites that break `git blame`.
- Reviewers can check the stated reason against the code in front of them.

**Cons:**
- It adds comment volume in exactly the places that are already subtle.
- The reason can itself go stale — an upstream bug gets fixed and the workaround stays.

**Decision:**
If removing or simplifying the code would be a mistake,
and the code alone does not show why,
the reason goes at the code.
The commit message may also explain it, but must not be the only record.

Mitigate the staleness cost by writing the reason as a falsifiable condition
and linking the issue that would close it,
so a reader can check whether it still holds.

This is a rule because a reason that is needed to avoid breaking the code
has no motivated reason to live somewhere unreachable.

## Example

### Bad
```rust
let config = load_config()?;
drop(guard);
apply(&config)?;
```

The `drop` reads as noise, and the next reader removes it.
The commit that added it said "fix hang in config reload", which nobody will see.

### Good
```rust
let config = load_config()?;
// `apply` re-acquires the registry lock, so release it here or the two deadlock.
drop(guard);
apply(&config)?;
```

A workaround, written so that a reader can tell when it stops applying:

```rust
// serde_json rejects a leading byte order mark (serde-rs/json#1115), and the
// S3 console adds one to objects uploaded through the web UI. Remove once the
// upstream fix lands: #412.
let body = body.trim_start_matches('\u{feff}');
```

## When to Flag

- `#[allow(...)]` with no justification at the attribute.
- An explicit `drop`, `sleep`, `yield_now`, `black_box`, retry count, buffer size, or magic constant with no nearby reason.
- An operation that appears redundant: a clone of something already owned, a re-read, a no-op branch, an empty match arm.
- A deviation from the pattern used elsewhere in the same module.
- A commit message that explains a constraint which still binds, where the code carries no trace of it.

## When NOT to Flag

- The reason is evident from the surrounding code or from a name such as `sleep_before_retry`.
- The code is a direct implementation of a contract already stated in the item's `///`.
- The reason is about the change rather than the code — that is W004.
