# W008: guidance-in-attribute-messages

**Level:** default

## Problem

Rust has three places that deliver text to exactly the person doing the wrong thing,
at exactly the moment they do it:

- `#[must_use = "…"]` fires when a return value is dropped.
- `#[deprecated(note = "…")]` fires at the call site of an obsolete API.
- `expect("…")` fires when a precondition turns out to be false.

Leaving the message empty throws that delivery away
and pushes the reader back to searching documentation they have already not read.
A bare `#[deprecated]` says an API is going away without saying what to use instead,
which is the only part the caller needs.

`expect` has a second, subtler failure:
messages written as error descriptions ("failed to read config")
duplicate what the panic already conveys,
while the useful content is the assumption that turned out to be wrong.

## Pros / Cons / Decision

**Pros of filling in these messages:**
- The text reaches the reader with no lookup, at the point of the mistake.
- Two of the three are compiler-delivered, so they cannot be missed.
- A deprecation note that names the replacement turns a warning into a mechanical fix.
- `expect` messages phrased as expectations state an invariant,
  which makes the panic self-diagnosing.

**Cons:**
- A bare attribute is faster to write, and reviewers rarely insist.
- Expectation-phrased panics read a little oddly in output:
  `panicked at 'HOME should be set by the login shell'`.

**Decision:**
`#[must_use]` and `#[deprecated]` carry a note saying what to do instead.
`expect` messages state the precondition being relied on, in "should" form.

## Example

### Bad
```rust
#[must_use]
pub fn with_retries(self, n: u32) -> Self {
    // ...
}

#[deprecated]
pub fn connect_v1(addr: &str) -> Result<Client, Error> {
    // ...
}

let home = env::var("HOME").expect("error getting HOME");
```

### Good
```rust
#[must_use = "`with_retries` returns a new builder; the receiver is left unchanged"]
pub fn with_retries(self, n: u32) -> Self {
    // ...
}

#[deprecated(since = "2.1.0", note = "use `connect` and pass `Tls::Disabled`")]
pub fn connect_v1(addr: &str) -> Result<Client, Error> {
    // ...
}

let home = env::var("HOME").expect("HOME should be set by the login shell");
```

## When to Flag

- `#[must_use]` with no note, where the reason for ignoring the value being a bug is not obvious from the name.
- `#[deprecated]` with no `note`, or a note that does not name the replacement.
- An `expect` message describing the failure — "failed to", "error", "could not" —
  rather than the expectation that was violated.
- `unwrap()` in non-test code where an `expect` could state the precondition being relied on.
- A builder or pure function where dropping the return value is meaningless, with no `#[must_use]` at all.

## When NOT to Flag

- `#[must_use]` on a type whose name already carries the message, such as a `Guard` or `MustUse` wrapper.
- Test code, where a panic message is the assertion and reads as one.
- `unwrap()` on a value whose `Some`-ness was established on the preceding line.

## Related Work

The standard library recommends that `expect` messages
"describe the reason you _expect_ the `Option` should be `Some`",
and suggests phrasing them around the word "should"[^1].

[^1]: https://doc.rust-lang.org/std/error/index.html#common-message-styles
