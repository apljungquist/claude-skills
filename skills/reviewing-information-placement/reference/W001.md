# W001: encode-dont-document

**Level:** default

## Problem

A fact about how an item must be used is stated in prose
when the type system could have enforced it.
Prose is checked by nobody,
so it drifts out of step with the code and then misleads.
A type is checked at every call site,
including the ones whose author never read the documentation.

`fn set_timeout(t: u64)` documented as milliseconds
accepts a value in seconds without complaint,
and the mistake surfaces as a timeout that is a thousand times too short.

## Pros / Cons / Decision

**Pros of encoding a fact in the type system:**
- It cannot go stale, because a mismatch stops compiling.
- It reaches every caller, not only the ones who read the documentation.
- It converts a class of runtime failures into compile errors.

**Cons:**
- More types to name, and conversion code at the boundaries where primitives arrive.
- A newtype for a fact nobody would get wrong is friction with no return.
- Some encodings (typestate, sealed traits) cost more complexity than the mistake they prevent.

**Decision:**
When a fact can be expressed in the type system, express it there.
Keep prose for what remains unexpressible.
Do not write a doc comment whose content the signature could have carried.

## Example

### Bad
```rust
/// Disconnects the client.
///
/// `timeout` is in milliseconds.
/// `force` decides whether in-flight requests are aborted rather than drained.
/// `connect` must have been called first, or this panics.
pub fn disconnect(timeout: u64, force: bool) {
    // ...
}
```

### Good
```rust
/// A duration in milliseconds, as the wire protocol encodes it.
pub struct Millis(pub u64);

/// What to do with requests that have been sent but not answered.
pub enum InFlight {
    Drain,
    Abort,
}

impl Client<Connected> {
    /// Disconnects the client, waiting up to `timeout` for the server to acknowledge.
    pub fn disconnect(self, timeout: Millis, in_flight: InFlight) -> Client<Idle> {
        // ...
    }
}
```

The unit, the meaning of the flag, and the ordering requirement
are now enforced rather than described.

## When to Flag

- A doc comment stating a unit, a range, or a scale that a newtype could carry.
- A `bool` parameter whose meaning is explained in prose rather than by an enum.
- A doc comment saying "call `x` before `y`", where typestate or a consuming method could enforce it.
- A doc comment saying an enum may gain variants, instead of `#[non_exhaustive]`.
- A doc comment saying a type must not be constructed directly, instead of private fields or a sealed trait.
- A doc comment restating an invariant that a constructor could establish once.

## When NOT to Flag

- The primitive is the wire format at an FFI, `serde`, or database boundary,
  and the newtype exists immediately inside it.
- The item is a private helper with a single call site in the same module,
  where the type machinery would cost more than the mistake.
- The fact is not type-expressible: performance characteristics, why an approach was chosen, external constraints.
