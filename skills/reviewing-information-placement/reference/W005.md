# W005: contract-in-doc-not-body

**Level:** default

## Problem

A fact the caller must obey — a precondition, a panic, an error condition,
a unit, a required ordering, a side effect, whether it blocks, whether it is cancellation-safe —
is written as a `//` comment inside the function body.

Callers see the signature and the rendered rustdoc.
They do not see the body,
and in a dependency they often cannot see it at all.
The information was written where its audience is not.

The same failure occurs when the fact is written nowhere:
the caller then discovers the precondition by violating it in production.

## Pros / Cons / Decision

**Pros of putting the contract in `///`:**
- `cargo doc` and IDE hover surface it at the call site, which is where the decision is made.
- `# Panics`, `# Errors`, and `# Safety` sections are lintable,
  so their presence can be enforced in CI rather than by reviewer attention[^2].
- Writing the contract forces the author to work out what it actually is,
  which routinely removes panics that turn out to be avoidable.

**Cons:**
- It duplicates what a careful reader could derive by reading the body.
- Conventional sections are ceremony on a three-line function.

**Decision:**
Facts a caller needs go in `///` on the public item, in the conventional sections.
Reasoning that only concerns the implementation stays in the body.
List every precondition under which a public function does not panic.

## Example

### Bad
```rust
pub fn parse_duration(s: &str) -> Duration {
    // Panics unless the suffix is s, ms, or us.
    // Callers must trim the string first.
    let (value, unit) = s.split_at(s.find(|c: char| c.is_alphabetic()).unwrap());
    // ...
}
```

### Good
```rust
/// Parses a duration such as `"250ms"`.
///
/// # Panics
///
/// Panics if `s` has no unit suffix,
/// or a suffix other than `s`, `ms`, or `us`,
/// or leading or trailing whitespace.
pub fn parse_duration(s: &str) -> Duration {
    let (value, unit) = s.split_at(s.find(|c: char| c.is_alphabetic()).unwrap());
    // ...
}
```

A fallible function states what the error variants mean,
which is what the caller has to branch on:

```rust
/// Uploads `body` to `key`, replacing any existing object.
///
/// # Errors
///
/// Returns [`Error::TooLarge`] if `body` exceeds 5 GiB, the single-request limit.
/// Returns [`Error::Throttled`] if the bucket is rate limiting;
/// this is retryable and carries the server's suggested delay.
pub fn put_object(&self, key: &Key, body: &[u8]) -> Result<(), Error> {
    // ...
}
```

## When to Flag

- A `//` comment inside a body that states something a caller must do or avoid.
- A public function that can panic, with no `# Panics` section.
- A public function returning `Result`, with no `# Errors` section explaining the variants.
- A public `unsafe fn` with no `# Safety` section (see W006).
- Units, ordering requirements, blocking behaviour, or side effects documented in the body.
- A doc comment that describes the algorithm instead of the contract.

## When NOT to Flag

- Private helpers whose callers are all in the same module and can read the body.
- Panics that are unreachable given a precondition already stated on the same item.
- Test code, where the body is the audience.
- Trait implementations whose contract is stated on the trait.

## Related Rules

- W001 — prefer to make the precondition unrepresentable rather than documented.
- W006 — the `unsafe` case, which needs both a caller-facing and an implementation-facing statement.
- W007 — usage explained by an example rather than by prose.
- `reviewing-rust-code` D045 — public items with no documentation at all.

## Related Work

C-FAILURE requires error, panic, and safety considerations in the item's documentation[^1],
and `clippy::missing_errors_doc`, `clippy::missing_panics_doc`, and `clippy::missing_safety_doc`
make the presence of those sections machine-checkable[^2].
