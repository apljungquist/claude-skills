# W004: transition-rationale-in-commit

**Level:** default

## Problem

A change lands with a subject line and no body.
The problem it solves, the effect on users, and the alternatives that were tried and rejected
exist only in a chat thread and in the author's memory.

A reviewer then has to reconstruct the goal from the diff in order to judge whether the diff achieves it,
which is the wrong direction of inference.
Later, someone deciding whether a constraint still applies
has nothing to check it against.

Unbacked claims are a specific case:
"speeds up parsing" cannot be confirmed, refuted, or noticed when it stops being true.

## Pros / Cons / Decision

**Pros of stating the transition in the commit body:**
- The reviewer can evaluate the change against a stated goal instead of guessing it.
- Numeric claims become falsifiable, and a later regression can be measured against them.
- The record survives the chat tool, the issue tracker migration, and the author's departure.

**Cons:**
- It is writing time on top of the change itself.
- Many changes genuinely need nothing beyond a subject line.

**Decision:**
The commit body states the problem, the effect a user would notice,
and — where a choice was made between plausible options — what else was considered and why it lost.
Claims about performance, memory, or size carry numbers.
Mechanical changes may omit the body.

## Example

### Bad
```
perf: speed up parsing
```

### Good
```
perf(lexer): replace the regex tokenizer with a hand-written scanner

Parsing the 10 MB manifest in our integration suite took 46 ms, of which
41 ms was inside `Regex::new`: the pattern was rebuilt on every call.

Caching the compiled `Regex` in a `OnceLock` was measured first and reached
9 ms, but keeps the dependency and its 400 KB of binary size. The scanner
reaches 3 ms with no dependency, at the cost of roughly 80 lines that now
have to be maintained by hand.

Fixes: #412
```

The rejected alternative is the part that saves the most time later,
because it stops the next person from trying it again.

## When to Flag

- A non-mechanical commit whose body does not state the problem being solved.
- A claim of improved performance, memory use, binary size, or latency with no measurement.
- A change that picks between plausible approaches with no statement of why.
- A body that paraphrases the diff — "renames `foo` to `bar` and updates the callers" — instead of explaining it.
- A trade-off that was knowingly accepted and left unstated.

## When NOT to Flag

- Changes fully described by their subject: dependency bumps, formatting, a mechanical rename.
- The reasoning is a constraint on the current code and is recorded there per W003,
  with the commit referencing it rather than repeating it (W009).
- `fixup!` commits that will be autosquashed into a commit that does carry the body.

## Related Rules

- W003 — the other half of the split; reasons that bind the current code.

## Related Work

The kernel's patch submission guide[^1] requires exactly this content:
an underlying problem, the impact on users,
numbers behind any claimed improvement,
and the trade-offs accepted —
on the grounds that the body "should make sense to a competent reader
who has long since forgotten the immediate details of the discussion".
It is also where the "why, not how" formulation for commit bodies comes from[^2].

[^1]: https://www.kernel.org/doc/html/latest/process/submitting-patches.html
