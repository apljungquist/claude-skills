# W006: safety-two-sided

**Level:** rule

## Problem

`unsafe` needs two different documents with two different audiences,
and they are routinely collapsed into one or reduced to a formality.

- `# Safety` on an `unsafe fn` states the obligations the **caller** takes on.
  Without it, the API cannot be used soundly by anyone who did not write it.
- `// SAFETY:` above an `unsafe` block states how **this** code discharges the obligations it relies on.
  Without it, the block cannot be audited;
  a reviewer has no stated claim to check, so review degrades to "looks fine".

Writing one and not the other leaves a real gap.
Writing either as "must be valid" or "this is safe" leaves the same gap with more words.

## Pros / Cons / Decision

**Pros of keeping both:**
- Each `unsafe` block carries an argument that an auditor can check against the code.
- Callers get an explicit obligation list rather than having to infer it from the implementation.
- Both are lint-visible: `clippy::missing_safety_doc` and `clippy::undocumented_unsafe_blocks`.

**Cons:**
- Verbose for thin FFI wrappers, where nearly the same sentence appears on both sides.

**Decision:**
Every `unsafe fn` has a `# Safety` section naming what the caller must guarantee.
Every `unsafe` block has a `// SAFETY:` comment naming the invariants it relies on and why they hold here.
Neither substitutes for the other.

This is a rule because the failure mode is undefined behaviour
and because the standard library holds itself to it.

## Example

### Bad
```rust
/// Reads `len` bytes starting at `ptr`.
///
/// # Safety
///
/// `ptr` must be valid.
pub unsafe fn read_bytes(ptr: *const u8, len: usize) -> Vec<u8> {
    unsafe { slice::from_raw_parts(ptr, len) }.to_vec()
}
```

"Valid" is not a contract: valid for reads or writes, for how long, aligned how,
and what happens when `len` is 0.
The block itself carries no argument at all.

### Good
```rust
/// Reads `len` bytes starting at `ptr`.
///
/// # Safety
///
/// `ptr` must be valid for reads of `len` bytes and must remain so for the
/// duration of the call. `ptr` must be non-null and aligned for `u8` even when
/// `len` is 0. The referenced memory must not be mutated by another thread
/// while this call is in progress.
pub unsafe fn read_bytes(ptr: *const u8, len: usize) -> Vec<u8> {
    // SAFETY: the caller guarantees `ptr` is non-null, aligned, and valid for
    // reads of `len` bytes for the duration of the call, which is exactly what
    // `from_raw_parts` requires. The resulting slice does not outlive this
    // expression, so the "no concurrent mutation" window is the call itself.
    unsafe { slice::from_raw_parts(ptr, len) }.to_vec()
}
```

## When to Flag

- An `unsafe fn` with no `# Safety` section.
- An `unsafe` block with no `// SAFETY:` comment, including inside an `unsafe fn`.
- A `# Safety` section that says only "must be valid" or "use with care",
  without naming validity for what, for how long, and under what alignment or aliasing.
- A `// SAFETY:` comment that asserts the conclusion — "this is safe", "checked above" —
  without naming the invariant or where it was established.
- A `// SAFETY:` comment that restates the caller obligations
  instead of explaining how they are discharged here.

## When NOT to Flag

- An `unsafe impl` whose safety argument is on the impl itself rather than on each method.
- A safe function wrapping unsafe internals, where the caller has no obligations
  and the block carries the argument.
- Test code that constructs deliberately invalid values, where the comment states that intent.

## Related Work

The standard library's own policy[^1] requires each `unsafe` operation inside an `unsafe fn`
to be enclosed in its own block with its own `SAFETY:` comment
explaining "why the block is safe, which invariants are used and must be respected" —
that is, the implementation-side document, distinct from the caller-side `# Safety` section.

[^1]: https://std-dev-guide.rust-lang.org/policy/safety-comments.html
