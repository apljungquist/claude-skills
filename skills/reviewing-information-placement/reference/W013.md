# W013: operator-info-in-logs

**Level:** default

## Problem

Information an operator needs while the system is misbehaving —
what it was attempting, with which inputs, and what it will do next —
is written as a code comment.

Comments do not exist at runtime.
The person reading logs during an incident cannot see them,
frequently cannot get to the source at all,
and is working under time pressure that makes reading source the wrong move even when possible.

The same failure appears in error types:
an error that says "request failed" without the identifying value
tells the operator that something is wrong but not which thing,
so the message cannot be acted on and cannot be aggregated.

## Pros / Cons / Decision

**Pros of putting operator-facing facts in events and errors:**
- The information reaches its audience at the time it is needed.
- Structured fields make it queryable, so incidents can be scoped rather than eyeballed.
- Error `Display` text propagates to callers and to the top-level handler that reports it.

**Cons:**
- Log volume costs money and buries signal when overdone.
- Messages become an interface that consumers grep for, which makes them awkward to change.
- Identifying values in logs can be personal data or secrets.

**Decision:**
If the audience for a fact is an operator rather than a developer,
it goes in a tracing event or an error message, not in a comment.
Errors carry the value needed to identify what failed.

## Example

### Bad
```rust
// If this fails the whole sync is abandoned, and the next run starts over from
// the last checkpoint, so partial progress in this batch is lost.
let batch = fetch_batch(&cursor).await?;
```

The consequence is real and worth knowing,
but the only person who can read it is someone already looking at this line.

### Good
```rust
let batch = fetch_batch(&cursor).await.inspect_err(|error| {
    tracing::warn!(
        %error,
        %cursor,
        "batch fetch failed; sync will restart from the last checkpoint"
    );
})?;
```

with the error carrying its own identifying context:

```rust
#[derive(Debug, thiserror::Error)]
#[error("failed to fetch batch at cursor {cursor}")]
pub struct FetchError {
    cursor: Cursor,
    #[source]
    source: HttpError,
}
```

## When to Flag

- A comment describing a runtime consequence — retry, fallback, data loss, restart, degraded mode —
  with no corresponding event or error text.
- An error type whose `Display` omits the value needed to identify what failed.
- A log message that describes the code path rather than the situation:
  `"in handle_batch"` instead of what went wrong and what happens next.
- A comment explaining what a failure means for the system as a whole.

## When NOT to Flag

- Comments about compile-time or development-time concerns, which have no runtime audience.
- Libraries emitting no events by deliberate policy, where the information is surfaced through error types instead.
- Hot paths where logging is deliberately omitted and a comment says so —
  that comment is a W003 rationale and belongs there.
- Values that must not be logged: credentials, tokens, personal data.
  Log a stable identifier instead of the value.
