# W010: todo-links-issue

**Level:** default

## Problem

A `TODO` carries a plan — what should be done, under what condition, with what caveats —
in a location that has no owner, no state, no due date, and no way to be closed.

Nothing schedules it.
Nothing notices when the blocking condition clears.
Nobody is notified when the author leaves,
and the plan then becomes unactionable
because the context it assumed is gone.
Because markers cannot be closed, they accumulate,
and a file with fifteen of them has effectively zero.

A `TODO` is a good pointer and a bad container.

## Pros / Cons / Decision

**Pros of moving the plan to an issue:**
- The tracker has an owner, a state, a priority, and a discussion thread.
- Closing the issue makes the marker checkably stale, which gives `D012` something to test against.
- The code keeps a one-line pointer instead of a paragraph nobody reads.

**Cons:**
- It requires a tracker and the discipline to file before committing.
- A bare `TODO` is faster to write, and filing has enough friction that the note may not be written at all.
- Issue links rot when a project migrates trackers.

**Decision:**
A `TODO` or `FIXME` names an issue.
The marker states what the code does now that it should not;
the plan for changing it lives in the issue.

## Example

### Bad
```rust
// TODO: this is O(n^2). We should build a HashMap of ids up front, but that
// changes the ordering guarantees, so we would need to sort afterwards, and
// sorting needs Ord on Widget which we do not have yet. Probably worth doing
// after the v3 refactor lands. -- ap
for widget in &widgets {
    if selected.contains(&widget.id) {
        // ...
    }
}
```

### Good
```rust
// TODO(#412): quadratic in `widgets.len()`; `selected` should be a set.
for widget in &widgets {
    if selected.contains(&widget.id) {
        // ...
    }
}
```

The observation stays at the code, where a reader profiling this loop will find it.
The plan, its blockers, and the sequencing move to `#412`, where they can be discussed and closed.

## When to Flag

- `TODO`, `FIXME`, `HACK`, or `XXX` with no issue reference.
- A marker carrying more than about one sentence of plan.
- A marker attributed to a person but not to an issue.
- A marker whose condition ("after the v3 refactor") nothing will ever check.

## When NOT to Flag

- `todo!()` and `unimplemented!()`, which are code rather than notes,
  and which fail loudly on their own.
- Example code, scratch files, and generated code.
- Projects with no issue tracker.
  There the plan belongs in module documentation or a decision record (W012),
  which is still not the marker.
- A marker that is purely a pointer and carries no plan: `// TODO(#412)`.
