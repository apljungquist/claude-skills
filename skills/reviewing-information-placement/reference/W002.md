# W002: change-relative-comment

**Level:** rule

## Problem

A comment describes the code relative to a state that no longer exists:
"now uses", "previously", "the new parser", "changed to return `Result`".
The sentence is meaningful only to someone who saw the version being contrasted against,
and that audience shrinks to nobody within a release or two.

Such comments also go stale with certainty rather than by accident.
The next change makes "new" false,
and a comment saying "previously we used regex"
survives three rewrites until it names a version nobody can find.

Commented-out code is the same failure in a more expensive form:
it is a copy of an old revision that the compiler no longer checks,
kept in a place where git already keeps a better copy.

## Pros / Cons / Decision

**Pros of banning change-relative statements from code:**
- Comments stay true indefinitely, because they describe only what is there.
- Git already stores the previous state losslessly, and `git log -S` searches it.
- It removes a category of comment that is guaranteed to become wrong.

**Cons:**
- During a staged migration, a pointer to the old path is genuinely useful.
- A reader who wants the history must now run `git log`, which is a slower lookup.

**Decision:**
Code and doc comments describe the current state only.
Statements about the change go in the commit message.
A transitional state that must be signposted gets a `TODO` with an issue (W010),
which describes the present shortcoming rather than the past.

This is a rule because there is no motivated reason to record the past in a place that cannot be updated,
and because the git history is strictly better at it.

## Example

### Bad
```rust
// Previously we tokenized with a regex, but that turned out to be too slow.
// The new scanner is hand-written and does a single pass.
fn scan(input: &str) -> Vec<Token> {
    // ...
}

// Old implementation, kept for reference:
// fn scan_regex(input: &str) -> Vec<Token> {
//     RE.find_iter(input).map(Token::from).collect()
// }
```

### Good
```rust
/// Splits `input` into tokens in a single pass.
fn scan(input: &str) -> Vec<Token> {
    // ...
}
```

with the contrast recorded where it is true — in the commit that made it:

```
perf(lexer): replace the regex tokenizer with a hand-written scanner

The pattern was rebuilt on every call, so `Regex::new` accounted for
41 ms of the 46 ms spent parsing the 10 MB fixture.
```

## When to Flag

- "new", "now", "previously", "used to", "no longer", "changed", "was", "as of", "in this PR", "in this commit"
  used in a `//` or `///` comment to contrast with an earlier revision.
- Commented-out code, with or without an explanation.
- A version-history or changelog block at the top of a source file.
- `/// Added for #123` or `// Part of the v3 migration` on an item that is simply part of the code now.

## When NOT to Flag

- `#[deprecated(since = "…", note = "…")]`.
  It is an attribute rather than a comment, the compiler delivers it, and describing a transition is its purpose (W008).
- Crate-level `//!` documentation that intentionally serves as release notes,
  or a generated changelog included with `#![doc = include_str!("../CHANGELOG.md")]`.
- A comment about *external* history:
  "libfoo below 2.1 returns the wrong length here" describes the current environment, not our change.
- Incidental uses of the words: `Instant::now()`, a type named `NewClient`, a field named `previous_cursor`.
