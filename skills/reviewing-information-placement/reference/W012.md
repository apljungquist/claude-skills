# W012: cross-module-decision-needs-a-home

**Level:** default

## Problem

Some decisions belong to no single file:
which async runtime the workspace uses,
how errors are modelled across crate boundaries,
which layer may depend on which,
why one dependency was chosen over an equivalent.

Written as a comment, such a decision sits in whichever file happened to be edited that day,
where nobody looking for it will think to look.
Written in a commit message, it is unreachable (W003).
Written nowhere, it is relitigated every few months,
and each round arrives at a slightly different answer,
so the codebase ends up with two error strategies and half a migration.

## Pros / Cons / Decision

**Pros of a decision record:**
- One durable, greppable, reviewable location that no refactor moves.
- The decision can be explicitly superseded rather than eroded, so the current state is knowable.
- A new contributor can read the set and understand the shape of the system in an afternoon.

**Cons:**
- A directory that needs maintaining, and records describing an architecture that has since drifted.
- Ceremony that a single-crate project will not repay.
- Splitting rationale across two places means a reader may find only one of them.

**Decision:**
A decision that spans modules gets a record under `docs/decisions/`,
stating the context, the decision, and the consequences,
with a status that can become superseded.
Code references the record instead of re-explaining it.
Decisions local to one module go in that module's `//!` documentation instead.

## Example

### Bad
```rust
// We use tokio rather than async-std here because the hyper version we depend
// on requires it, and because the scheduler already needs tokio::time. Note
// that this means the blocking module has to use spawn_blocking rather than
// its own threads. The same applies in net and store.
```

Parked in one module, describing three others, and duplicated in each of them
by the next person who needed to explain the same thing (W009).

### Good

`docs/decisions/0007-tokio-as-the-only-runtime.md`:

```markdown
# 7. Tokio as the only async runtime

## Status

Accepted

## Context

`hyper` 1.x requires tokio's I/O traits, and the scheduler needs a timer.
Supporting a second runtime would mean an abstraction layer over both, or
feature-gated duplicate implementations in `net`, `store`, and `blocking`.

## Decision

We depend on tokio directly and do not abstract over the runtime.

## Consequences

Blocking work must go through `spawn_blocking` rather than raw threads, so
that it is accounted for by the runtime. Crates in this workspace may depend
on `tokio` directly. A consumer using another runtime cannot use this library.
```

and at the code:

```rust
// Blocking work goes through the runtime, not raw threads:
// docs/decisions/0007-tokio-as-the-only-runtime.md
task::spawn_blocking(move || index.rebuild()).await??;
```

## When to Flag

- A rationale comment whose subject matter is not local to the file it sits in.
- The same rationale appearing in several modules.
- A commit body carrying an architectural decision that will outlive the commit.
- A convention followed across the codebase that is written down nowhere,
  so that a deviation cannot be identified as one.
- A decision reversed without any record of the reversal.

## When NOT to Flag

- Decisions local to one module — those belong in the module's `//!` documentation.
- Single-crate projects where the crate-level `//!` doc is a sufficient home.
- Implementation choices that a reader can evaluate from the code in front of them.

## Related Rules

- W003 — reasons local enough to belong at the code.
- W009 — reference the record rather than restating it in each module.

## Related Work

Nygard's argument for these records is that large specification documents go stale and unread,
while "small, modular documents have at least a chance at being updated" —
and that without a record of the motivation,
a maintainer can only accept a decision blindly or change it blindly[^1].

[^1]: https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions
