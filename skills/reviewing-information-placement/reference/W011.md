# W011: commit-subject-is-a-changelog-entry

**Level:** default

## Problem

Under conventional commits the subject line is machine-consumed:
its type selects the semantic version bump,
and changelog generators emit it verbatim to people deciding whether to upgrade.

Writing the subject for the reviewer instead —
"address review comments", "fix CI", "wip", "small tweak" —
produces release notes that tell the reader nothing,
and quietly breaks the version bump when a breaking change is filed under `refactor`.

The audience for the subject and the audience for the body are different people.
The subject is read by someone upgrading, out of context, months later.
The body is read by someone examining this change specifically.

## Pros / Cons / Decision

**Pros of writing the subject as a changelog entry:**
- The changelog becomes generated rather than hand-maintained, so it cannot silently fall behind.
- The version bump follows from the history instead of from someone's memory.
- Naming the user-visible effect forces the author to check that there is one.

**Cons:**
- Some commits genuinely have no user-visible effect and need a type that generators discard.
- It imposes structure on work-in-progress commits that will be rewritten anyway.
- Descriptions long enough to be useful sometimes do not fit a 50-character subject.

**Decision:**
Write the subject as the line a consumer would read in release notes:
type, optional scope, imperative description of the effect.
Reviewer-facing notes go in the body.
A change that breaks callers is marked with `!` or a `BREAKING CHANGE:` footer,
never left to prose in the body.

## Example

### Bad
```
fix: address review feedback
```

```
refactor: change Client::connect signature
```

The second silently breaks every caller,
and nothing in the message triggers a major bump.

### Good
```
fix(retry): stop retrying non-idempotent requests after a timeout
```

```
refactor(client)!: take `Tls` explicitly in `Client::connect`

Defaulting to TLS-on meant a plaintext endpoint could only be reached by
constructing the client through the builder, which is not discoverable.

BREAKING CHANGE: `Client::connect` now takes a `Tls` argument. Pass
`Tls::Enabled` to keep the previous behaviour.
```

## When to Flag

- A subject describing the review process rather than the change:
  "address feedback", "fix review comments", "wip", "cleanup", "small fixes".
- A change to a public signature or observable behaviour
  with no `!` and no `BREAKING CHANGE:` footer.
- A subject naming the files touched rather than the effect:
  "update client.rs and tests".
- A type that misstates the change: a bug fix filed as `chore`, a feature filed as `refactor`.
- A subject that only a reviewer of this diff could interpret.

## When NOT to Flag

- `chore:`, `ci:`, `test:`, `build:`, and `docs:` commits with no user-visible effect;
  generators drop them by design.
- `fixup!` commits that will be autosquashed.
- A terse subject on a change whose effect genuinely is fully described by it.

## Related Work

The specification's stated purpose is automatically generating changelogs
and automatically determining the semantic version bump from the types that landed[^1].
C-RELNOTES requires that significant changes be documented
and that breaking changes be clearly identified[^2],
which is what the `!` marker and the footer exist to carry.

[^1]: https://www.conventionalcommits.org/en/v1.0.0/
[^2]: https://rust-lang.github.io/api-guidelines/documentation.html#release-notes-document-all-significant-changes-c-relnotes
